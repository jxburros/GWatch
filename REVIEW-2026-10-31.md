# GWatch 0.8.5 — comprehensive review (31 October 2026)

Scope: the whole repository at commit `ed46466` (branch `claude/vibrant-pasteur-m2lrmm`, identical to `main`), reviewed from six angles: verification (build, tests, scanners), security, backend architecture, web frontend/UX/accessibility, the agent/MCP/packaging/docs edges, and the competitive landscape. Everything marked **verified** was run or read in this session; competitor facts come from web research on the same day and are approximate.

---

## 1. Verdict in one paragraph

GWatch is a far more serious product than its "calm home-network monitor" framing suggests. Six and a half weeks of development (first commit 17 September 2026, 454 commits, roughly 63k lines of Go, 36k lines of Go tests, 20k lines of dependency-free JavaScript) have produced a monitor that already sits past the midpoint of the "between Uptime Kuma and Zabbix" gap it aims for. The engineering quality is high and unusually consistent: every check in this session passed (build, vet, staticcheck, Go tests on all packages, the MCP module, 394 JavaScript unit tests, the TypeScript check, and all 185 Playwright end-to-end tests), the security audit found no Critical or High issue, and the design documents are better than most commercial products ship with. The weaknesses are real but are mostly about **adoption and sustainability** rather than correctness: a non-OSI licence that will keep it out of every distro and most homelab channels, unsigned Windows installers on its primary platform, a release pipeline heavier than the team, a version cadence that outruns publication, a database write held under the engine's global lock, and an agent self-install that writes an unhardened root unit while the packaged unit is hardened. Nothing found is a reason not to use it on a home network today.

## 3. Security

**Headline:** no Critical or High findings. The four Phase-1 claims in `ROADMAP.md` were checked against code and all hold:

- Endpoint tokens: `internal/api/automation.go:300-331` refuses to save a hook without a token of at least 8 characters unless the admin explicitly opts out; comparison is constant-time; failures are rate-limited per IP.
- Script placeholder injection: `internal/actions/actions.go:102-139` never splices raw text into sh/bash/PowerShell/Python/Node code (environment variables or quoted literals instead); git arguments are expanded per-argument and refuse values that become options; URLs forbid placeholders in scheme and host.
- Signed self-update: `internal/update/update.go:422-508` has no skip path. The signature is fetched before the download, binds asset name and version, the SHA-256 sidecar is an extra check rather than a fallback, downgrades are refused, and packaged builds refuse to self-update.
- Secrets at rest: AES-256-GCM with a 0600 key file; one shared `SecretFields()` list drives storage, masking and restore. The documented caveat remains: the key sits beside the database, so it protects copies and dumps, not a local reader.

**Done well (verified):** proxy headers are ignored unless `--trusted-proxies` is set and the loopback-admin principal is refused to any request carrying a forwarding header (`internal/api/trustedproxy.go`, `auth.go:291-302`); layered CSRF and DNS-rebinding defence (Origin/Sec-Fetch-Site checks comparing host and port, JSON content-type required, `SameSite=Lax` cookie, `frame-ancestors 'none'`); an explicit fail-closed policy table with a test that diffs router against table (`policy.go:68-273, 349-375`); Argon2id passwords with timing equalisation for unknown users; per-credential-kind rate limiting; API keys can never create, edit or run code-executing checks (`api.go:744-770`); fully parameterised SQL with constant `ORDER BY`; near-zero XSS surface (five `innerHTML` writes, all constant, strict CSP with no inline script); outbound credential hygiene on redirects in checks, metrics fetch and the MCP client; SHA-pinned GitHub Actions, `contents: read`, no `pull_request_target`; the curl installer verifies an ed25519 signature with an inline-pinned key; non-root Docker with only `NET_RAW`.

**Findings (all Low or Info):**

| ID | Finding | Where | Suggested fix |
|---|---|---|---|

## 4. Backend architecture and code quality

**Strengths**

- Clean, acyclic dependency direction: `main` → `api` → `engine` → `store` → `model`, with checks/actions/mailer/sysmetrics as leaves. Concrete types with function-typed injection points (`RunFunc`, `SendFunc`, swappable `recordResult`) rather than interface sprawl. Right-sized for a single binary.
- **One schema, three databases.** The DDL is written once in SQLite form and *translated* for PostgreSQL and MySQL through a small dialect interface and a mini SQL lexer (`internal/store/dialect.go`, `dialect_postgres.go:24-80`, `sql_lex.go`), and CI runs the suites against real Postgres 16 and MySQL 8. Unusual and effective.
- Migration safety: read-only version check first, refuses a newer DB, copies the file before migrating, schema `IF NOT EXISTS` plus catalogue-guarded `ADD COLUMN`, numbered data migrations each committed with the version bump (`store.go:520-650`).
- Staged-then-committed result processing: `process` computes transitions on a copy, writes result + state + incident in one transaction, and only then commits the copy to the live map; a regression test injects a failing write and proves no alert is lost (`internal/engine/process.go:343-346`, `regression_test.go:52-75`). The "one open incident per node" invariant is enforced by a nullable `UNIQUE(active_node_id)` column.
- Dependency-aware alerting that probes the parent synchronously before paging a child; DST-correct maintenance windows per IANA zone; sleep/suspend detection via wall-clock `Round(0)`; shutdown budgets sized to stay inside SCM/systemd stop timeouts; a `WithoutCancel` work context so in-flight alerts outlive scheduler cancellation.
- Rollups raw → 5 min → 1 h → 1 day with aligned-window upserts; the README's bounded-growth claim holds (daily summaries grow at one row per check per day).
- Exceptional CI breadth: Windows, Linux (race detector, both SQL servers, all three SQLite drivers, staticcheck, govulncheck, systemd install lifecycle, shellcheck, Playwright + axe, real-server browser tests, link check), macOS, Docker amd64 and armv7 smoke, deb/rpm. A CI script asserts Authenticode signing happens before hashing.
- Comment quality is consistently "why", with issue numbers. Errors are wrapped (`%w` 173 vs `%v` 17). No panics or `log.Fatal` in library code.

**Weaknesses**

| Impact | Item |
|---|---|
| High | **Database write under the global engine lock.** `process` takes `e.mu` at `process.go:57` and holds it through `recordResult` at `:347` (a transaction with fsync). Every result write blocks the scheduler tick, `States()`, `Overview()` and every other result. This, not the 1-second tick, is the ceiling for several hundred checks on an SD card or a remote Postgres. (Verified in code this session.) |
| Medium | Persistent write failure becomes a hot loop: on error the state is not advanced, so the check is due again next tick at ~1 Hz, bounded only by the semaphore. No backoff, no disk-space or integrity check. |
| Medium | The single-writer mutex applies to PostgreSQL and MySQL too (`serializeWrites()` is true for every dialect), so a server deployment inherits SQLite's concurrency model. |
| Medium | `rollupRange`'s legacy-UTC-day → local-day reconciliation SQL (`history.go:113-165`) is the hardest code in the repo to change safely. |
| Medium | Test suite: zero `t.Parallel`, 44 sleeps, no clock injection in tick/retention. Correct but slow and time-coupled. |
| Low | `internal/api/api.go` at 2,015 lines / 142 routes; the "update a node" use case exists only as an HTTP handler, so bulk and MCP paths re-walk it. Package-level SNMP state in `checks` is cleared from the API layer. Two coexisting migration mechanisms. Hand-rolled logger without levels or structure. 183 discarded errors unaudited. |

## 5. Web frontend, UX and accessibility

**Architecture.** A hash router with lazy per-view `import()`; every element built through one `h()` hyperscript builder (`web/components.js:9-31`), no innerHTML templating; per-view `mount()` returning `{refresh, destroy, update, themeChanged}`; one shared ref-counted `EventSource` with a 15-second polling fallback and visibility-aware teardown (`web/api.js:206-273`); hand-rolled canvas charts with a "Timestack" overlay mode; a pure, unit-tested tidy-tree/radial layout for the network map rendered to SVG. Rendering is surgical rather than full re-render: node rows are recycled and diffed by string signature (`views/nodes.js:196-300`), and `refreshRegion` preserves focus and scroll across rebuilds. The design system is real: 138 CSS tokens, five status renderers, modals with focus trap and `inert`, roving-tabindex menus, a `field()` helper that wires `aria-describedby`/`aria-invalid` automatically. Theme, accent and density are set pre-paint from localStorage.

**Visual design (screenshots examined).** It looks genuinely good: Barlow for prose and Kode Mono for every number and label give a coherent instrument-panel feel; glowing status numerals, uppercase mono card titles and a restrained dotted grid are distinctive without being gimmicky. Light and dark are at parity, with the light theme not an afterthought. The wallboard is the best page in the product: a headline sentence ("2 nodes down"), big counters, an attention list with dependency reasons ("Unavailable because Gateway is down"), trends, certificates and service health, exactly what a TV needs. Nothing reads as dated.

**Accessibility (independently verified).** axe over 72 page states found zero serious or critical issues. Dialogs are `role=dialog aria-modal` with focus trap and restoration; every time chart is a focusable `role=img` with keyboard-stepped tooltip and a "View as table" fallback; status pills are deliberately not live regions; reduced motion and forced colours are handled; a contrast test parses the CSS tokens and checks every pair in both themes without a browser (`tests/web/contrast.test.mjs`). The README's claims hold.

**UX strengths.** First run redirects to a six-step tour; every empty widget has an empty state; 18 opt-in coach-mark tips; a Help-launched tutorial that walks real pages; adding a node needs only name and host; Discover and Bulk edit sit beside Add node. Status semantics are consistent and contrast-tested.

**Weaknesses**

| Impact | Item |
|---|---|
| High | Monolithic view closures: `views/dashboard.js:103 mount()` is 775 lines, `node-detail.js:13` 594, `node-editor.js:268` 480, `discovery.js:30` 462. Testable only through DOM harnesses, impossible to type-check meaningfully. |
| Medium | `@ts-check` covers 5 of about 40 files, with `strict: false`; "type checked" is true of the toolkit, not of any view (~8k lines). |
| Medium | Charts page copy contradicts itself after the 0.8.5 "blank charts" change: canvas says "Tick the metrics…", sidebar says "Nothing ticked: GWatch picks the checks" (`views/charts.js:116` vs `chart-config.js:379`). |
| Medium | A `go run` dev build immediately shows "GWatch 0.8.5 is available" over the empty dashboard (`app.js:434-452`). |
| Medium | The new per-node colour fills the whole name cell and map box and fights the status cues; the picker shows a blue swatch labelled "None". |
| Low | `.page-bar` is not a landmark (18 moderate axe `region` notes); h1→h3 jumps; `/wall` has no h1; chart canvas font stack names IBM Plex rather than the UI fonts (`charts.js:19-20`); rail still says "Service healthy" while the API-down banner shows; a new node has no default check; duplicate line at `app.js:272-273`. |
| Low | The Go↔JS mock shape contract (`internal/api/mock_contract_test.go` ↔ `tests/web/mock-contract.test.mjs`) is genuine but GET-only and one-directional: it stops the mock drifting behind the API, not the UI sending what the API expects. |

## 6. The agent, MCP server, packaging and docs

**Agent (`cmd/gwatch-agent`, 11k lines).** Push-only by default with bearer tokens; `serve` mode for pull with per-source lockout; a check-in that returns a closed five-field struct; held readings persisted to a triple-bounded spool (age, 4,000 entries, ~8 MB) that survives restarts; ed25519-signed self-update with two pre-swap proofs and offline rollback; packaged builds refuse to self-update so apt/brew/winget never fight it. Measured: 11 MB static binary, about 9 MB RSS. Linux collection is the richest (hwmon temperatures, PSI pressure, ZFS, cgroup limits); Windows has Hyper-V over WMI but no temperatures; **macOS has no CPU utilisation at all** and shells out to `ioreg`/`netstat`, which the README's "dependency-free" claim does not mention. Compared with node_exporter, Telegraf, Netdata and Glances, the agent's distinguishing choice is a fixed reading schema with no metric language and no remote execution, which is both its differentiator and its ceiling.

**MCP server (`mcp/`).** Built on the official `modelcontextprotocol/go-sdk`, stdio transport, 9 read and 8 write tools with proper `ReadOnlyHint`/`DestructiveHint` annotations; write tools exist only with `--allow-write` **and** a readwrite key, and the server enforces 403 regardless. The server instructions explicitly tell the model all monitoring strings are untrusted, and tool output wraps data in labelled blocks: prompt-injection handling that most hobby MCP servers lack. Tested against a fake that mirrors the real policy table plus an opt-in e2e against a real server. The in-app Settings › AI & MCP page serves a versioned, downloadable agent skill and notices when a newer one exists.

**Packaging.** Three OSes × three or four architectures, Inno Setup installers, deb/rpm via nfpm, Homebrew, winget, multi-arch Docker; 51 + 37 required assets per release. The packaged systemd units are unusually hardened (dedicated user, `CAP_NET_RAW` only, `ProtectSystem=strict`, `SystemCallFilter`, `RestartPreventExitStatus=78` so a bad config does not crash-loop). `install.sh` verifies an ed25519 signature before installing.

**Weaknesses**

| Impact | Item |
|---|---|
| High | **`gwatch-agent install` on Linux writes an unhardened root unit** (`internal/serviceinstall/install.go:91-108`: no `User=`, no `Protect*`, no capability bounding) while `packaging/nfpm/gwatch-agent.service` is fully hardened, and `docs/AGENT-DECISIONS.md` recommends the self-install path for unattended machines. (Verified in code this session.) |
| High | Windows installers remain Authenticode-unsigned in practice; SmartScreen warns on the primary platform. The plumbing exists (`scripts/authenticode.ps1`, Azure OIDC), the identity is not provisioned. |
| Medium/High | Release pipeline is heavier than the team: `release.yml` is 1,432 lines, duplicates CI's job inline, then hands off to a reusable workflow and Node toolkit in a separate org repo that `.release/README.md` admits has never performed a real publish. Three of the last eight versions (0.7.0, 0.7.1, 0.8.1) are marked "not published" and 0.8.2–0.8.5 "not yet released" while the README already says "What's new in 0.8.5". |
| Medium | No apt/dnf repository, so deb/rpm installs never update unattended. Docker's first account still needs `docker exec`. Re-running the Windows installer keeps the first port/LAN choice. |
| Low/Medium | `ROADMAP.md` is headed "Status (September 2026)" and Phase 1 still describes fixed problems in the present tense; the "no multi-site" non-goal has effectively been crossed by remote collectors, which the roadmap squares with a paragraph. |

**Documentation** is broad (USER-GUIDE 1,458 lines, API 1,618, 18 files in `docs/`) and written in one plain, candid voice ("GWatch hands you a lot of rope", "We collect nothing, because there is nowhere for it to go"). `docs/AGENT-DECISIONS.md`, a 726-line living decision record with "rejected" and "revisit if" per entry, is the single most unusual artefact in the repo. Every legal document says it is not lawyer-reviewed.

**Process.** 392 of 454 commits are authored by Claude, merged through 32 `claude/<adjective>-<scientist>` branches plus parallel worktree sub-branches, in bursts of up to 136 commits a day. The throughput and the uniform voice across code, comments and docs follow from that; so does the fact that the review bottleneck is one human, and nothing in the history shows a second reviewer.

**Ahead of the Uptime Kuma tier:** dependency map with outage reach and suppression, at-least-N cross-node rules in a UI, SNMP with name-based port picking, a hardware agent that sees Docker and Hyper-V, remote collectors for a second site, Postgres/MySQL option, signed self-update, encrypted backups, Windows-service-first install, axe-tested accessibility, no telemetry, and a first-party MCP server. No beta peer matches this operations maturity.

**At parity:** the basic check types. **Behind the same tier:** alert channel count (no generic webhook as a first-class channel, no Apprise, Signal, Home Assistant, Mattermost), and **no public status page**, which every uptime peer has and which the README never mentions.

**Behind Zabbix/Checkmk/LibreNMS:** SNMP depth (MIBs, LLDP/CDP topology auto-discovery), template ecosystems, host-side service auto-discovery, proxies at scale, SLA reporting, escalations, mobile apps. The network map is hand-declared dependencies, not discovered topology.

**Genuinely unique or rare**

1. Matter smart-home device readings through a python-matter-server sidecar: no standalone monitor does this; only Home Assistant plugins and a UniFi release candidate come close.
2. Hyper-V guest monitoring from an 11 MB dependency-free agent.
3. Outage-reach visualisation on a dependency map in a single lightweight binary.
4. At-least-N cross-node notification rules without an expression language.
5. Remote collectors (a paired agent running the built-in checks at a second site) at this weight class.
6. A first-party, scope-aware, injection-conscious MCP server with an in-app versioned skill, free and self-hosted; only Zabbix 8 (RC), Checkmk (paid), Netdata Cloud (paid), Domotz (SaaS) and Grafana ship one.
7. Accessibility CI with axe on every route in both themes; no competitor advertises this.
8. One SQLite schema translated to Postgres and MySQL by a lexer, tested against both in CI.
9. `docs/AGENT-DECISIONS.md` as a living decision record.

**Licence risk.** The GWatch Community License is Commons-Clause-style (no resale of unaltered copies, no paid hosting without significant modification) plus mandatory name/logo retention in the UI, and says itself it is not open source. Consequences: no Debian, Fedora, Alpine, Homebrew core, NixOS-free or Unraid Community Applications listing; exclusion from awesome-selfhosted (OSI required); the hosting partners through which non-technical homelabbers meet Kuma, Beszel and Netdata (PikaPods, Elfhosted, Cloudron, Umbrel) are precisely the "paid hosted service" the licence forbids; "source-available" reads as a rug-pull risk to the r/selfhosted audience after the Netdata and Zabbix licence episodes; and no community fork can carry the project if the maintainers stop. The commercial surface it protects, reselling an unmodified free home monitor, is close to zero. AGPL-3 plus the existing trademark policy would achieve almost the same goal with OSI standing.

**Realistic target user.** The prosumer homelab or small-office IT generalist, often on Windows, with 10–100 devices: a router and switch (SNMP), a few servers, NAS, Hyper-V or Docker hosts, websites and APIs, some smart-home gear; who wants calm, dependency-aware alerts, long history, backups and no cloud. Specifically: Windows-centric admins who dislike Linux-only stacks, PRTG free-tier users who hit 100 sensors, Home Assistant users who also want infrastructure monitoring, people burned by Netdata's cloud push, and people who want an AI assistant to query monitoring without a SaaS.

## 8. Prioritised recommendations

**Before 1.0 (trust and reach)**

1. Harden the agent's self-written systemd unit to match `packaging/nfpm/gwatch-agent.service` (`internal/serviceinstall/install.go:91-108`).
2. Provision the Authenticode identity; nothing else on the Windows path matters as much as removing the SmartScreen warning.
3. Add a `toolchain` directive to `go.mod` and bump it each release so source builds do not land on a vulnerable 1.26.0.
4. Reconcile versions with reality: either publish 0.8.2–0.8.5 or stop advancing the number until the pipeline can ship. Consider replacing the 1,432-line release workflow and the external toolkit with goreleaser + nfpm, which the repo's existing packaging files already mostly fit.
5. Reconsider the licence. If the goal is "no one sells unmodified GWatch", AGPL-3 plus `TRADEMARKS.md` does it and unlocks every packaging and discovery channel.

**Soon (correctness and scale)**

6. Move `recordResult` out from under `e.mu` in `process` (stage under the lock, write outside, re-lock to commit), and add backoff on repeated write failure.
7. Let PostgreSQL/MySQL dialects run with real concurrency (`serializeWrites()` false) once the write paths are audited for it.
8. The seven Low security items; L-5 (viewer-readable script code) and L-7 (backup password floor) are each an afternoon.

**Product**

9. A public status page is the one table-stakes feature every uptime peer has and GWatch lacks.
10. A generic webhook as a first-class alert channel (triggers cover it, but newcomers look in the channel list), then Apprise or Home Assistant.
11. Default a new node to one ping check so the first result arrives without a second step.
12. Fix the Charts copy contradiction and the dev-build update nag; soften the node-colour fill.

**Code health**

13. Split the three largest view closures and the 2k-line `api.go`; extend `@ts-check` to views with `strict` on.
14. Introduce clock injection into the engine's tick and retention loops and start using `t.Parallel`.
15. Refresh `ROADMAP.md` (it is dated September and describes solved problems in the present tense) and note the macOS and Windows agent gaps in the README's hardware claims.
